When people talk about working hours, I think of a different kind of count. Here the shift is 24/7. And I'm not the one working 24 hours a day: it's the software I built, as a hobby, in a little over a week.

This is the first chapter of a diary. I'll tell you what I'm building, how I got here, what went wrong along the way and what I learned from it. In the next chapters, each lesson gets a text of its own, with the data and with the mistakes.

## How it started

On a Saturday night, I had a simple idea: what if I could open several AI sessions at the same time, each one taking care of part of the work? One writes the code, another writes the tests, another reviews. Maybe a few terminals and a script would do.

It didn't stay in the terminals. That same night the idea became a desktop app with an engine that follows a workflow defined in a configuration file. Each step of the workflow is run by an AI agent (Claude, Codex or Grok), and the engine only decides which step comes next. It doesn't improvise.

That was the first important decision, and I only understood how big it was later. The part that decides "what comes now" is plain, predictable code that always does the same thing. AI only steps in where intelligence is needed: writing, testing, reviewing. That keeps the process auditable. When something goes wrong, I know exactly at which step it happened and why.

The workflow is the same one a development team would follow:

- **Develop:** an agent implements the task in an isolated copy of the project, without touching what already works.
- **Test:** another agent, one that didn't write the code, writes the tests.
- **Review:** a third one reviews, preferably with a different model from the one that wrote it. An AI reviewing another AI's work catches things the first one wouldn't see.
- **Approve:** the code only goes in if it passes the tests and the review. Wherever I want to decide, the workflow stops and waits for me. No automation goes over that approval.

That same night the build, continuous integration and a test environment for each change came in. I went to bed with a skeleton that already looked like a production line.

## Sunday: the first real run, and the first mistake

On Sunday I did what everyone does with a new toy: I ran it for real.

The first real run failed. A detail in how an agent's answer was validated brought the workflow down at the very end. The second one, already with the full development workflow, worked, but it took almost 40 minutes, and the continuous integration step ran four times in a row before it passed. That was my first hint that the problem wouldn't be writing code.

Sunday was also when the supervisor was born: an AI that only enters the scene when a step fails. It investigates what happened and proposes how to get unstuck.

The first time it worked, it suggested fixing the code directly. It looked helpful, but I saw the risk: a supervisor that fixes code outside the workflow skips exactly the steps that make it safe, such as testing, review and approval. I redefined its role right there. The supervisor takes care of the workflow, not of the code. When the problem is in the code, it hands the task back to the workflow's agents, with the evidence and the hypotheses, and the code goes through every step again.

That rule became a principle of the project: **automation never crosses a human approval**, not even the supervisor.

## Monday, the quiet day

Monday was the calmest day of the week. No runs, few requests. It was an architecture day: separating the engine from the interface, hardening the app's security and writing a context document that every agent reads before starting. That document was born out of an emergency: the conversation with the AI had grown so long it was reaching its memory limit, and I asked for a summary of everything. The summary became the house manual.

Looking back, that quiet day is what made everything after it possible.

## The day the tool started developing itself

On Tuesday, I opened several sessions in parallel, each one in an isolated copy of the project, and almost all of them started the same way: "run the app so I can see it".

In the middle of the afternoon, I opened a session just to jot down ideas in a text file. Fifteen minutes later, the ideas were already registered tasks, and the app got a backlog screen where each task can be handed to a workflow. By midnight there were more than 50 registered tasks, almost all of them born from a conversation.

And then I started having the tool itself solve the tasks.

Around 4:40 pm, the first task was delivered by the tool itself. Almost in the same minute, I wrote a sentence to Claude that now sounds like a prediction: that I wasn't going to abandon it, I'd keep using it, only that, in a little while, inside my own tool.

An hour later, around 5 pm, came the turning point: the tool started generating more AI work than I did using AI directly. From then on, the curve never went back. Within a few days, more than 90% of the AI work in the project was coming from the tool. My sessions changed their role: instead of writing code, I followed, diagnosed and decided.

## Five agents, one file

On Tuesday night, excited, I set five tasks to run at the same time.

Each agent worked in its own copy of the project, without getting in the others' way. It worked really well until the end, when it was time to put everything together. Four of the five failed at the last step, because of a conflict: two agents had changed the same part of a file. All the work had already been done and paid for, and it got stuck at the exit door.

That night taught me a lesson that will get a whole chapter: parallelism is cheap to start and expensive to finish. The answers came in layers:

- **Group related tasks** into a single run, trading several conflicts for a single path.
- **Merge the work locally**, on my own computer, instead of depending on an external service for every change. That took the queues and the continuous integration minutes I didn't control out of the short loop. The success rate of the runs jumped from about half to more than nine in ten.
- **Plan ahead**, instead of solving the conflict afterwards.

And it was that last layer that opened the way to the first night.

## The first night

To leave the computer working on its own, something was missing: someone to organize the work. So I created an AI Product Owner.

It reads the backlog and lays out a plan in stages. For each group of tasks, it predicts which files will be touched, points out where there may be a conflict and puts the tasks that would fight over the same file into different stages. Resolving conflicts moved from the moment the code is merged to the moment of planning. During the day, I write down the ideas. At night, the plan runs.

I remember the last message I sent that night: "cancel the monitor, I'm going to sleep and leave the PC running".

The plan ran on two parallel tracks. At 11:30 pm, the first two tasks. Almost at 1 am, the next two. Then at 1:30, 2:30 and 3 am. The last run finished at four in the morning.

I woke up to **10 tasks delivered, tested and merged**. None failed. Not a single message from me between midnight and seven in the morning. And among that night's tasks was one that put the supervisor itself on call. The tool was, literally, improving itself while I slept.

The machine only stopped at four because the plan ran out. There was no more planned work. That detail changed how I think about the project: for 24/7, what matters most may be how many hours of well-defined work are ready when I go to sleep.

## The night it all almost went wrong

Not everything went smoothly. An hour before the first night started, I accidentally opened a second copy of the app, pointing at the same working folder. Both started writing to the same state at the same time. Runs that were alive were marked as interrupted, duplicate runs showed up and the plan stopped, pointing at cancelled tasks.

I asked the AI: "can't you fix it for me?".

And it could. Since all of the app's state lives in readable files, not in a closed database, the AI read the code that writes the plan, understood the format, made a backup, pointed each item at the right run and lifted the pause. In two minutes the plan was running again, without losing any work. At that moment, I felt like I had superpowers.

The flaw and the superpower had the same origin: files have no lock. Two processes wrote to the same place. The definitive fix became a task that same day, and today the app guarantees a single instance per working folder. But the lesson stayed: a system the AI can read is a system the AI can fix.

## The second night: non-stop

Before the second night, the tool spent the late afternoon reorganizing its own code so that several agents could work at the same time without bumping into each other. Screens split into their own files, lists with one entry per line, tables generated automatically. No change in behavior, only in format. It sounds like little, but it's what made it possible to scale.

And it scaled. On the second night the machine didn't stop. There were **about 25 tasks**, more than twice the first night, with up to **5 agents working at the same time**. There were four conflicts, and all four were resolved without me. At seven in the morning there was still a run going.

There was a single blocker, and I like it. In the middle of the night, a task reached a point where the workflow requires my approval. It waited for more than two hours, until I woke up. That's exactly the right behavior: the machine works the whole night, but it doesn't make my decisions for me.

That same night, the credits of one of the AI providers ran out, and the reviewer switched to another model. Until then, I thought AI credits would never be the limit. With five agents in parallel, the consumption per hour more than doubles.

## The bottleneck that moves

The next day, I put four heavy runs in parallel, and my computer froze. I had to cancel everything.

That's when I noticed a pattern. The bottleneck never goes away, it moves. First it was the external continuous integration service. Then, the conflicts when merging the code. Then, the way the code was organized. Then, planning. Now it was the machine itself: processor and memory. The answer was similar to a human team's: leave the heaviest tests for when a version is wrapped up, not for every task.

The following night, the cost of tests per run dropped to a fraction of what it was. And the bottleneck moved again: now it's the time the test suite takes to run.

## Two hours mine, 22 hours the AI's

When it sank in, it was shocking. I had no idea what it means to have agents working 24/7.

If I organize the workflows, the agents and the backlog well, I can interact with the system for two hours a day. In the first hour, I review what was done during the night and approve or ask for fixes. In the second, I prepare the work for the next 24 hours. The rest is AI working.

This project is what I do in my spare hours. And that's exactly what changed my mind: two hours a day of one person can turn into 24 hours of work, as long as there is well-defined work to do.

And there's never a shortage of work. Ask any company whether there's anything to do in technology, and the answer is always the same: there's a million things. What's missing is defining them, organizing them in a backlog and having a production line that executes them with quality. The backlog is the factory's fuel.

I'm not at two hours yet. On the second night, I still sent more than a hundred messages during the day, many of them to plan the night. But the path became clear: my time stopped being the limit.

## What I've learned so far

The numbers draw attention, but the surprises were worth the most. Each one of them will become a chapter.

**The bottleneck isn't writing code, it's testing.** Adding up the time of each step, testing took longer than development. Much of that time was an agent waiting for a command to finish, with conditions that were never met. Adjusting the tests brought the cost of that step down to a fraction of what it was.

**The most expensive token is an AI waiting.** The most expensive run of the project delivered nothing. An agent spent its time checking, again and again, whether a process had finished, blocked by a permission it didn't have. Waiting, checking status and comparing results is work for plain code. AI steps in when there's a decision to make.

**Git was made for humans.** People change a few lines at a time. Agents in parallel don't. Two agents that add a line at the end of the same list run into a conflict, even without any real contradiction between them. With several agents, even the layout of the files becomes an architecture decision.

**Refine first or react later?** The traditional way invests heavily up front: refinement, prototypes, trying to predict every detail. When generating gets cheap, waking up to a finished proposal and saying "not like this, like that" costs less than trying to describe everything in a vacuum. The working increment becomes the cheapest specification there is.

**What I ask for three times becomes automation.** "Run the app so I can see it" became a step that produces evidence of every delivery, with screenshots and logs. "Register this as a task" became a workflow of its own. Even the voice dictation I used became a feature. My repeated requests were, almost always, the next piece of the product.

## A week in numbers

- **More than 200 commits** since the first one, on a Saturday night.
- **More than a hundred tasks** registered, almost all born from a conversation.
- **10 tasks** on the first night and **about 25** on the second, with up to **5 agents** at the same time.
- **More than 90%** of the AI work in the project coming from the tool itself.
- **Not a single** human approval crossed by automation.
