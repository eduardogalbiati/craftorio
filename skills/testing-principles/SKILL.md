# Testing principles

The language skill tells you the framework and commands. These rules decide what a good test is.

## Seams first

A **seam** is a public boundary where behaviour can be observed without reaching inside:
an exported function, a class's public methods, an HTTP endpoint, a CLI command.

Before writing tests, list the seams you will test at the top of your answer:
- prefer seams that already exist, at the highest level that still gives a fast, deterministic test;
- fewer is better, often one per change;
- never test private functions directly. If the only way to test something is to reach inside,
  report it as a testability finding instead of exposing internals.

## A good test

- Describes **what** the unit does, in the test name ("rejects an expired token"), not how.
- Goes through the seam only; survives a refactor that keeps behaviour.
- Checks one logical behaviour; asserts on outputs and observable state, not on call counts or
  call order of your own collaborators.
- Covers the happy path, edges (empty, null/zero value, limits, unicode, time zones) and
  expected errors.
- **Never hands a DOM node, a sandbox / `vm` object or another large object graph to an
  assertion**: compare a primitive (`el === null`, a count, a string, `Array.from(list)`). A failing
  assertion serialises both operands for its message, and a node of a fake DOM or a sandbox drags
  the whole page or context with it: one such failure grew a test process past 70 GB and stalled
  every other run on the machine.

## Where a test goes

- A new test goes into the existing test file of the area it covers (the project's testing docs
  name the split, e.g. one file per module or per area); a new area gets a new file.
- Never append to a large catch-all test file because it is the one that already covers "everything":
  every run editing it conflicts with the others.

## Find the right tests: the code → tests map

Pointing at the tests that cover the code is what keeps a change from breaking them (TDAD:
regressions fell 70% when agents were given the code → tests map).
- When the project has a map (this orchestrator: `docs/agents/test-map.md`, generated by
  `npm run docs`; a step may also name one in its prompt), **search it** for the source files the
  change touches (don't read it whole): each line lists the test files that import that file, then
  those reaching it through other files. Those are the tests to run and to extend.
- No map: the test files that import the module (a search for its name in the test folders).

## Read results, not logs (agent mode)

Agents pay for tests by reading them: a full log is hundreds of KB of passing tests and stack traces.
- Prefer the project's failures-only output. This orchestrator's `npm test` (and `npm test -- <files>`)
  detects an agent and prints **one JSON line**: the counts and, per failure, the test, file, line,
  the error's first lines and expected/actual; the human-readable report is in the file its
  `human_log` names (read only the lines you need). Other runners: their quiet, failures-only
  options (the language skill says which).
- When the orchestrator runs tests for you (a ```run-tests block, the suite step), you get the same
  summary: never re-run the tests to read their output again.

## Tests first: acceptance tests written before the code

In a tests-first workflow (AI Development, local hero, #220) the test writer writes the
**acceptance tests** from the task and its criteria, before any code:
- derive them from the task and the public interfaces it names, never from today's internals;
  a criterion that cannot be tested automatically is listed as not testable, never faked;
- the orchestrator runs them once right after (the red check): a test already green before any
  code guards existing behaviour or is wrong; a file that cannot run comes back to you (a whole
  extra turn, which re-reads your context);
- **each file must load before the code exists**: a module, export or file the change creates is
  loaded inside each test (or in a per-test helper), never at the top of the file, so a missing
  module fails each test on its own instead of crashing the file; before answering, run only the
  new files once to check they load and fail on the missing behaviour (the language skill names
  the pattern);
- **the developer never edits the acceptance tests written before it** (the engine refuses a turn
  that changes one, `protect_files`), and **may add its own internal tests**.
In the other workflows the rule stays: the developer never writes tests (only the test writer does).

## A project with no test runner

A project with no test command (a plain HTML site, a Markdown-only repository: no package.json,
go.mod, pom.xml, build.gradle, *.csproj or pyproject.toml, and the workflow's `test_command` empty)
has no test runner: nothing can run a test file there. Never invent one (no package.json, no
framework, no runner script added just to run your tests): the suite step does not run, the run goes
on to the build and the verification, reported as "Not tested: no test command" (#81). Say so in your
answer: each criterion is then not testable automatically, with how to check it by hand (open the
page, follow the link). Only when the task asks for a runner is adding one part of the change.

## Anti-patterns (reject them in your own tests)

- **Tautological test**: the expected value is computed with the same logic as the production
  code, so it passes by construction. Expected values come from literals, worked examples or
  the spec (`expect(total).toBe(15)`, not `expect(total).toBe(price * qty)`).
- **Implementation-coupled test**: mocks internal modules, inspects private state, or asserts
  which helper was called. It breaks on refactor and proves nothing about behaviour.
- **Horizontal slicing**: writing tests for imagined future behaviour. Test what the change does now.

## Mocking

- Mock only at system boundaries: network/external APIs, time, randomness, and sometimes the
  filesystem or database (prefer a temp dir or a test database).
- Never mock the module under test or code the project owns.
- If code builds its own clients internally (`new StripeClient()` inside a function), prefer
  injecting the dependency; if you cannot change production code, report it as a finding.

## Bug fixes: red before green

A regression test must fail against the unfixed code. Show it failing (run it before the fix,
or on the base commit) or explain why that is not possible. A test that never failed is not
evidence of a fix.

## Nobody can answer questions

You run unattended. When something is ambiguous (which seam, which expected value), choose the
option most consistent with the existing tests and code, and list it under **Assumptions** in
your answer.

## Fit the time budget (focused tests; the orchestrator runs the suite)

A test turn has a time limit; a killed turn loses its answer and the next attempt pays again, and
every minute a suite runs keeps your turn (and its whole context) open.

- Run only the focused tests of the change: the test files you touch, filtered to the tests you
  are writing (the language skill's "one file / test" command). A slow file (over a minute) runs
  **at most once per round**; don't rerun it to read a different part of its output: keep the
  output in a file.
- **The whole suite is the orchestrator's** when your workflow has a suite step (the
  software-development workflows, #177): it runs the project's suite once after your step, without
  an agent, and gives you only its failing tests (name, file, first lines of the error) and the
  path of its log. Never start the whole suite yourself there (the run notes it as a warning).
  Read the log only for the failures you fix, or have a sub-agent summarise it.
- Only when your prompt says nothing runs the suite after you (no suite step): run the full suite
  **once, at the end**, and a second time only after a fix, not to double-check.
- Never start a full end-to-end or mock run of the application (e.g. a workflow run script) unless
  the task asks for it: the suite already includes what the project wants run.

## Pre-existing failures: report them, don't chase them

When a test fails (yours, or one the orchestrator's suite reports), first find out whether the
failure is this change's:

1. Run **only the failing files** on the base commit. When your prompt gives a base checkout (the
   orchestrator prepares one, with its dependencies linked from the shared cache), run them there
   and never install anything in it. Otherwise a temporary worktree
   (`git worktree add --detach <temp folder> <base>`, run the files, then
   `git worktree remove --force <temp folder>`); when it lacks dependencies, say so in the
   reason rather than running a second full install. Never use a bare `git stash` (the stash is
   shared with other worktrees and runs).
2. A test that **also fails on the base** is pre-existing: list it in `preexisting_failures`
   (`test`, `file`, `reason` in one line) and move on. It does not make the step fail, and it is not
   investigated or fixed in this run (no log digging, no reproduction runs), unless the fix is
   trivial and in files this change already touches. The owner gets the list as a follow-up.
3. A test that passes on the base and fails on the branch is this change's: report it as usual
   (production bug vs outdated test).

## Done when

- every seam you listed has at least one test for the behaviour that changed;
- the focused tests of the change pass (or fail for a reported reason); the full suite was run once
  with the project's command only when no suite step runs it after you;
- every failure is reported as test name, error, and probable cause (production bug vs outdated test),
  and a failure that also fails on the base is listed as pre-existing instead.
