The issues of the project chosen in the header (#254), synced from its git platform: **GitHub** (gh CLI) or **GitLab** (glab CLI); Bitbucket is listed but has no sync yet. The default platform is in Settings › General › Backlog and can be switched on the screen. The last sync is kept in `<workspace>/backlog/<project id>.json` (shown instantly, a new sync runs each time the screen opens). **List** view (open/closed/archived filters, labels, task-list progress, the issue rendered as Markdown; an issue filed from a discovery card shows the card's badge, `card: <title>`, which opens the card read-only on the Discovery board, #258) or **Kanban**: **To do**, **In progress** (queued, running, failed, or its run succeeded but the issue is still open, e.g. its PR/MR isn't merged yet), **Waiting for approval** (its run is at a human gate; **Review approval** opens it), **Merged locally** (not pushed yet) and **Done** (closed on the platform). Select To do issues and **Assign workflow…** (workflows with a `task` input; their other inputs are asked once and remembered per project; simulation in developer mode): they wait in the project's queue (`<workspace>/backlog/<id>.queue.json`) and start in the order selected: **one at a time**, or as many as the free slots allow with Settings › Execution › **Concurrent runs** (the oldest first across projects, within the limit per project). With two or more issues selected, the dialog asks how to send them: **Separate runs** (the default: one run, branch and PR/MR per issue) or **One run for all**: one queued item, one run, one branch and one PR/MR that closes every issue (the note says what will happen: "3 issues → 1 run, 1 PR closing #53, #65, #77"); at most Settings › General › Backlog › **Issues per run** (5 by default). Every card of a group shows the same run (queued position, status, waiting, Done) with a "grouped with #a, #b" badge; removing one card from a queued group asks whether to take only that issue out of the group or cancel the group. Each run records its issues; `software-development` gets them as the `issue` (the first) and `issues` (every URL) inputs: for a group, the task lists every issue, the developer and the PR/MR account for each one, the review and the verifier check each one, and an issue the developer could not do stops at a gate (continue without it / stop), never dropped silently. The queue can be paused; it is paused when the app starts, when a start fails (budget, missing CLI) and when a queued issue's run fails. Each sync also reads the open PRs/MRs that refer to an issue (a closing keyword or a link to it in the description, `#<number>` in the title, GitHub's closing references) and shows them as badges linking to them; **Assign workflow…** warns about selected issues that already have one (or a run in progress or waiting) and skips them unless you assign them anyway; right before a queued issue starts, the queue checks again and skips it (saying why) if a PR/MR was opened for it since it was queued. The git platform is the **source of truth** for issues (#168): queued and roadmap items keep a read-only copy of each issue that every sync refreshes until the item starts, and right before a queued or roadmap item starts, its issues are read again from the platform: the run's task uses the current title and body, an issue closed meanwhile is skipped, and the run records the version it used (`updatedAt`). If the platform cannot be read, the run starts from the last sync (or the planned copy, when it is newer), logs a warning ("Issue #n read from the cache of HH:MM: …") and its card shows an **issue from cache** badge. Nothing writes local issue text back to the platform; only the explicit, previewed actions below do (Save to issue, create, close, epics). Runs started by hand are linked when their task or a text input mentions the issue URL or `#<number>`; **Enrich in Write & Review** on an open issue (list row, kanban card, expanded details) opens Write & Review prefilled with it (an enriched issue by default; title, number, URL, labels and body in the prompt; nothing starts by itself), and once its document is accepted, **Save to issue** replaces the description (the original kept in a collapsed block) or adds it as a comment, after a preview and your click; the issue is read again after the save. Such a run shows as "being enriched" / "enriched" and never moves the card's column
. **Roadmap** (a screen of its own, Code & Build › Roadmap, #254): the queue is a pool (items start whenever a slot is free); a roadmap is a plan. It lists **stages** in order, each with one or more items (a workflow with one issue or a group, its inputs, simulated or real), a name and a note on why this order, in `<workspace>/backlog/<id>.roadmap.json`. **Add to roadmap** in the Assign dialog plans the selection as a new stage; the plain queue's items can be moved in; a Product Owner proposal (JSON) is added or replaces the roadmap, always as **planned**. Stages and items move up/down or by drag, an issue can be dragged from one item to another, items are removed and their inputs edited. **Start** (optionally **Simulated**) runs the first stage's items in parallel within the concurrency limit; the next stage starts only when **every item of the current one finished successfully and merged** (a local merge, the PR/MR merge action, a simulation that succeeded, or a successful run of a workflow that never merges, `metadata.merges: false`, such as **Backlog Refresh**); a run waiting at a human gate keeps its stage open. A failed, cancelled or interrupted run **pauses** the roadmap with a notice: resume the run (Resume from step…: the new run takes the item's place), **Retry** or **Skip** the item, or **Stop** the roadmap; it never skips a failure nor answers a gate by itself. A start the roadmap could not make (kept work of an ended run, #170) pauses it the same way: the item shows its error, wrapped, with **Retry** (it asks: resume the old run or start from scratch) and **Skip**, and the page's alert offers **Retry**, **Skip** and **Show the item**, which scrolls to it; several such items ask in turn. **The bar** (#269) shows the roadmap's state as a dot before its name (blue and pulsing while running, amber paused, red paused by a failure, grey planned, green done), **Pause** (amber) and **Stop** (red, after a confirmation) with their icons, and a **⋮** menu with **Clear** and **Restore an earlier version…**; the filters (epic, Planned / All, date range, Group by epic) sit on a row above it. **Alerts** (#270): what the Board and the Roadmap have to tell you shows at the top of the page, one alert at a time with a counter ("1/3") and arrows, errors first: a roadmap paused by an item or the queue's error (red), a Backlog Refresh that is due or the retired `deprioritized` label (amber), local merges not pushed (light blue, with **Push…** and **Auto-push**). **Ask the Oracle about this failure** (#271): a card whose item failed, was interrupted or stopped, or could not start opens the Oracle beside the roadmap, already asking what happened to that run and what to do (a real question: it costs like any Oracle question); the Oracle may propose an action card, which runs only on your click. **Undo** (#281): removing or moving an item, a stage or an issue, renaming a stage, removing a cut line, Clear and Replace show a toast with **Undo** for 10 seconds; it puts back what that edit changed (items that started since keep their runs) or says why it cannot. The roadmap as it was before each of your last 20 edits is kept in `backlog/<project>.roadmap.history/` and restored from the ⋮ menu. Undo and Restore never stop a run nor answer a gate. **The item card** (#282) reads in three bands: its **issues** (the titles, then "4 issues · complexity 9") beside its **cost and time** (the estimate; once it runs, the real value against it with a verdict, a sign and a bar, the time being the run's live timer) and its **status** (the progress ring with the estimated %, the status and the current step, the fix round; then Retry / Skip, or move and Remove); the **Workflow band** with the workflow's name, **Open run →** or **Edit**, the **mode** toggle (Automatic / Validated, saved at once; locked while the item runs), the other inputs, and the **pipeline**: one station per stage of the workflow, always visible, done, at work (with the agent's name), sent back ("asked for fixes"), not reached yet, and the owner's gate that Validated adds ("Your check"); a station opens the run there; then the Product Owner's reason. The ring's estimate counts the steps done along the workflow's usual path, weighted by each step's typical time in past runs (never 100% before the end); hover or click it for the run's summary. A stage's rarely used actions are in its **⋮** menu: **Disable** / **Enable**, **Run this stage**, **Release here**, Run earlier / later and its note. **A disabled stage** (#284) is skipped while the roadmap runs: nothing of it starts, its cut line holds nothing and the stage after it runs as if it were not there; it stays in the list in its place, dimmed, with a **Disabled** badge, and is counted apart ("5 stages, 1 disabled"). With every enabled stage finished the roadmap is done and says how many disabled stages were left out; enabling one never starts it by itself. Start, Resume and Run this stage list the items whose workflow pushes and opens PRs while the default development workflow merges locally (their card says "Pushes a PR/MR"): **Switch them** to the default, or **Start anyway**. Long reasons, notes, errors and inputs wrap or end with … inside the card: the roadmap never scrolls sideways. A started roadmap continues after an app restart. Issue cards show their place ("Roadmap: stage 2"); an issue belongs to at most one planned item, assigning it to the queue asks first and takes it out of the roadmap, and items whose issues are all closed are skipped. **Group by epic** shows the roadmap's items under their issues' epics. **Live roadmap** (#164, a switch in a box below the last stage; on only while the roadmap runs, so turning it on asks to start it): when the last stage ends, the roadmap does not end: the Product Owner picks the next open issues (not in the roadmap or the queue, no open PR/MR or run in progress, not an epic, not flagged to enrich first, `complexity:n` up to a cap, lowest first) and adds them as new planned stages (a stage note says when, and what its answer cost), and the roadmap goes on, again and again. While it is on, the box turns a muted red with **LIVE** and a banner with a blinking dot sits on top of every Backlog view (last refill, **Turn off**). It stops by itself when nothing is left to pick or the daily budget (runs and refills over 24 h) is reached: the roadmap ends done with the reason and live stays on (Start tries again); a failure pauses it as usual, and turning it off lets the current stages finish. Refills only add planned stages: they never answer a gate. Settings › General › Live roadmap: the complexity cap (2), the stages per refill (3), the daily budget (US$ 50) and a sync before each refill. **Epics** (the Backlog's second tab, #138; an epic shows only there, #253: the Board's list, kanban, counts and filters leave epics out, and an epic cannot be selected, assigned to a workflow or planned in the roadmap): on GitHub an epic is an issue labelled `epic` (or of the organization issue type "Epic") whose **sub-issues** are its members; on GitLab a group epic, or an issue labelled `epic` whose members carry the scoped label `epic::<name>`. Each sync reads them into the cache; every card shows its epic as a badge (a click filters by it) and the **epic filter** (a select with counts, "No epic" included) narrows the list and the kanban, together with the labels and the search. The view lists each epic with its progress (open, closed, done in the roadmap) and members, the issues in no epic, **Auto-place new issues** (per project: a new issue the Product Owner registers, or the Issue Tracker files, joins the existing epic it clearly matches; a new epic always asks) and **Organize into epics…**, which asks the Product Owner to propose epics for the open issues. **Product Owner** (the robot button at the bottom right, every view): a built-in agent that opens a drawer on the right, with suggested questions ("Analyze the backlog and propose runs", "What should not run together?", "Build a roadmap", "Which issues are too big or unclear?", "Which issues are too big to run as one?", "Organize the open issues into epics") and a free text box. **Send to Product Owner (n)** (#169), next to **Assign workflow… (n)** when issues are selected (list or kanban), opens the drawer with them attached as removable chips (`#129`, `#130`) and an editable suggested question ("What is the best strategy to put these issues in the roadmap? Should any other open issue join them?"): nothing is sent until you press **Ask**, and the selection is kept. **Archive (n)** (#238), in the selection bar and in each open issue's **⋯** menu (at the right end of a list row, in the top right corner of a kanban card), closes the issues on the platform (GitHub: as not planned) and labels them `archived` (created, grey, when the repository lacks it), after a confirm that names them ("Close #12, #15 as not planned on GitHub and label them archived?"): they leave the Open view at once and show under the **Archived** chip (**Closed** keeps the finished work; the kanban hides them), where **Restore** reopens an issue and removes the label. An issue planned in the roadmap (planned or running item) or with a run in progress cannot be archived: its Archive is disabled with the reason ("Planned in stage 41: remove it from the roadmap first"); a failure (no permission, offline, CLI missing) is shown per issue and leaves it as it was, the others still go through. The Product Owner's report, its plans and the roadmap leave archived issues out (one cannot be added to a stage). Archive replaces the retired `deprioritized` label: issues that still carry it get a one-time alert offering to archive them. Attached issues are read in full and stay attached for follow-up questions until removed (or the conversation is cleared); the answer plans only them and lists, per group, similar open issues that could join as **suggested, not selected** checkboxes (unchecked: a checked one joins on **Assign…**, **Add to roadmap** and **Add all to the roadmap**). An attached issue closed meanwhile is struck through and left out of the proposal; the button is disabled while the Product Owner is answering. It reads the synced issues (bodies clipped unless the question names or attaches them), the queue, the runs in progress, local merges not pushed, the roadmap and the project's finished runs (agent time, cost, tokens, merge conflicts and the files they hit), plus the project's code, read-only. Each answer shows its cost and proposes **groups** (issues, workflow and inputs, why they belong together, files, stage), the issues that **must not run in parallel** and why, the issues to **enrich first** (#103), and each group's **size**: the sum of its `complexity:n` labels (3 when missing), a time and cost **estimate** from past runs of similar size, and a warning at complexity 7 (context limit) or 5 in a group (test time budget). Nothing is applied until you click: **Assign…** opens the Assign dialog prefilled (the issues selected as one run, the workflow and inputs), **Add to roadmap** plans the group as a new stage, **Add all to the roadmap** adds every group as planned stages. One agent call per question (Claude Code, the model and effort set in Agents, 15 min at most), refused when Claude Code reached a blocking monthly budget; developer and simulated mode answer from a simulated Product Owner (no model call). It never edits issues, starts runs or answers a gate. **Live progress** (#180): while it answers, the drawer shows under your question what it is doing, like a Claude Code conversation: an activity line with a spinner and a timer ("Starting the Product Owner…", "Reading src/roadmap.js", "Searching the code for dispatchRoadmaps", "Listing open issues (gh)", "Thinking…"), its last steps as a collapsible list ("6 steps"), then the answer as it is written, rendered as Markdown (the JSON block at its end never shows; the groups and their buttons appear when the turn ends). **Stop** ends the turn and keeps what was written, marked **Stopped**; a failure keeps it too, after the error; with no news for a minute the line says "Still working: last step 1 min ago". Simulated mode streams a few fake steps and the simulated answer. **Split what is too big** (#124): an issue of complexity 4–5, with more than 8 tasks, tasks in unrelated areas of the code, parts that could ship on their own, or the size of past runs that hit the context limit or the test time budget is flagged with its reasons, and the answer proposes 2–4 child issues (title, the parent's tasks each takes — every task in exactly one child —, complexity, stage: children of one stage can run together) and whether the parent becomes an umbrella or is closed; **Edit…** moves a task to another child, renames or merges children, and **Split** (or **Split + roadmap**, the children planned by stage with the workflow of the select next to the buttons, the default development workflow of Settings › General › Backlog until changed; the same select is next to **Create + roadmap** in the chat) files them, each with the parent's context, then adds a `- [ ] #n` task list to the parent or comments and closes it. **Epics** (#138): the answer places issues in existing epics (**Place in epic**) and proposes new ones (title, goal, members: **Create epic**), and names epics to merge or split; a drafted issue may name its epic, and **Create** places it there when "Place in epic" is checked. Everything that writes to GitHub/GitLab waits for your click (previews only in developer mode). The conversation is kept per project in `<workspace>/backlog/<id>.po.jsonl` until **Clear**. **Backlog Refresh banner** (#161): when the project's last successful Backlog Refresh run is older than Settings › General › Backlog › **Suggest a backlog refresh every** (24 h by default; Off) and its base branch got merges since (or no refresh ever ran), a warning in the page's alerts (#270) says "Backlog refreshed 26 h ago · 14 merges since" with **Refresh now** (the Start panel on `backlog-refresh.yaml`, prefilled with the project, its platform, the base and `since` = the last refresh's start; nothing starts until you press Start, simulated in developer mode) and **Dismiss for today** (kept in `<workspace>/backlog/<id>.refresh.json`). While a refresh run is live the alert says "Refreshing the backlog…" with a link to the run. When the run ends the Backlog syncs the project; the issues it updated show a **refreshed** badge for a day, and the issues it closed leave the roadmap as usual (an item whose issues are all closed is skipped). **Show on the map** (#375), on an issue card and in a list row's **⋯** menu, opens the project's city (Architecture › City) with the issue's expected footprint: the files its body cites (`file:line` and plain paths; globs are ignored), the files of the Product Owner's group for it (read from its saved answers, never asked again) and, after a run, the files that run changed, each building coloured by its source and the rest grey. A header shows the issue, the counts by district and zone and the share of the files in the Danger Zone; a predicted file the repository does not have yet is listed apart ("new file, expected in <district>" when a city plan rule matches it). After the issue's run it shows changed as predicted, predicted but untouched and changed but not predicted, with a hit rate kept per issue. No model call
